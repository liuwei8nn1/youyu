## 概述

DDD 分层架构由 Eric Evans 在《领域驱动设计》一书中系统提出。其核心思想是：**将复杂的业务系统按关注点划分为若干层，每层只做自己该做的事，并严格约束层与层之间的依赖方向**。

四层架构解决的核心问题：

| 问题 | 四层架构的答案 |
|------|----------------|
| 业务逻辑与框架代码纠缠 | 领域层纯净，与技术细节解耦 |
| 业务规则散落各处、难以复用 | 业务规则收敛到领域层，单一职责 |
| 数据库/消息等变化导致业务重写 | 依赖倒置，领域层依赖抽象不依赖实现 |
| 新人无法快速理解代码结构 | 目录结构即架构，分包即分层 |

> 💡 分层不是目的，**可维护性和业务表达能力**才是目的。分层的终极形态是：领域层成为可以脱离框架、脱离数据库独立运行和测试的核心资产。

## 总体分层结构

```
┌─────────────────────────────────────────────┐
│  Interfaces（用户接口层）                      │
│  接收请求 / 参数校验 / 响应格式化 / 协议适配     │
└──────────────────┬──────────────────────────┘
                   │ 调用
┌──────────────────▼──────────────────────────┐
│  Application（应用层）                        │
│  用例编排 / 事务控制 / 权限控制 / DTO 转换      │
└──────────────────┬──────────────────────────┘
                   │ 调用
┌──────────────────▼──────────────────────────┐
│  Domain（领域层） ★ 核心                       │
│  实体 / 值对象 / 聚合 / 领域服务 / 领域事件      │
└──────────────────┬──────────────────────────┘
                   │ 依赖倒置（DIP）：依赖接口，不依赖实现
┌──────────────────▼──────────────────────────┐
│  Infrastructure（基础设施层）                  │
│  数据库 / 缓存 / 消息队列 / 外部服务 的具体实现  │
└─────────────────────────────────────────────┘
```

**依赖方向**（严格单向，禁止反向）：

```
interfaces → application → domain ← infrastructure
```

- `interfaces`、`application` 依赖 `domain`
- `infrastructure` 依赖 `domain`（通过实现 `domain` 定义的接口）
- `domain` **不依赖**任何其他层
- `application` 不依赖 `infrastructure`（通过 `domain` 的 Repository 接口访问数据）

## 用户接口层 Interfaces

### 职责与作用

**用户接口层是系统的对外门面**，负责与外部世界的一切交互，是"协议适配器"而非"业务承载者"。

| 职责 | 说明 |
|------|------|
| 协议适配 | 将 HTTP/RPC/MQ/定时触发等外部协议转换为应用层可调用的方法 |
| 参数校验 | 请求参数的语法级校验（格式、必填、长度、枚举范围） |
| 请求/响应转换 | 将外部报文转换为应用层 DTO，将返回结果格式化为对外 VO |
| 响应格式化 | 统一包装返回结构、HTTP 状态码、错误信息映射 |
| 会话/鉴权入口 | 解析当前用户身份并传递给应用层 |

**关键原则**：

- ✅ 只做"翻译"和"分发"，不包含任何业务规则
- ✅ 禁止在 Controller 中编排业务、拼接数据
- ✅ 入参出参对象在此层定义，不直接暴露领域对象给外部

### 二级分包

| 子包 | 含义与职责 |
|------|------------|
| `controller` | 端点/路由定义，接收请求、调用应用服务、返回响应；只做协议适配 |
| `converter` | 接口层对象 ↔ 应用层 DTO 的转换器（请求对象转 DTO、DTO 转 VO） |
| `request` | 入参请求对象（含 `@Valid` 校验注解），不携带业务逻辑 |
| `vo` | 出参视图对象（View Object），面向展示层，字段按前端需要组织 |
| `dto` | 接口层与应用层之间传递的输入/输出对象（部分团队将 request/vo 合并到此包） |
| `listener` | MQ 消费者、外部事件监听入口；拿到消息后转交给应用层，自身不处理业务 |
| `task` | 定时任务入口（调度触发），业务处理仍委托应用层 |

> 💡 判断规则：凡是"外部怎么进来、结果怎么出去"相关的代码，都属于接口层；凡是"业务该做什么"的代码，都应在接口层之外。

## 应用层 Application

### 职责与作用

**应用层是业务用例的编排者（Orchestrator）**。它决定"针对一个用例，按什么顺序调用哪些领域能力"，但不负责"业务规则本身是什么"。

| 职责 | 说明 |
|------|------|
| 用例编排 | 组织领域对象/领域服务完成一个完整业务用例 |
| 事务控制 | 管理用例级事务边界（数据库事务、跨资源事务协调） |
| 权限与安全控制 | 校验当前用户是否有权执行该用例 |
| DTO 转换 | 将接口层 DTO 转换为领域对象，将领域结果转换为输出 DTO |
| 跨聚合协作 | 需要多个聚合协作时，由应用层编排（领域层不跨聚合直接调用） |
| 基础设施调用协调 | 通过领域层接口间接调用 MQ、缓存等能力 |

**与领域层的边界（最容易混淆）**：

| | 应用层 | 领域层 |
|--|--------|--------|
| 关注点 | "做什么、按什么顺序做" | "规则本身是什么" |
| 举例 | 下单流程：校验库存→扣库存→建订单→发消息 | 库存是否充足、订单金额如何计算 |
| 决策 | 不改变业务规则 | 是业务规则的唯一权威来源 |

**关键原则**：

- ✅ 应用服务可以是 `@Service` + `@Transactional`，允许持有 Repository 接口
- ✅ 应用层持有多数的 DTO，领域层不依赖 DTO
- ❌ 禁止把核心业务规则写在应用层（否则领域层会退化成一个空壳）
- ❌ 禁止在应用层直接操作数据库/MQ 具体实现

### 二级分包

| 子包 | 含义与职责 |
|------|------------|
| `service` | 应用服务（ApplicationService），一个方法对应一个用例，编排领域对象完成用例 |
| `dto` | 应用层输入/输出对象，跨层（接口层↔应用层↔领域层边界）传递 |
| `converter` | 领域对象 ↔ DTO 的转换器 |
| `assembler` | 装配器（可选），组装多个来源的数据形成完整输出对象 |
| `facade` | 门面（可选），对下层服务做聚合，供接口层或外部模块调用 |
| `event` | 应用事件/事件发布器（可选），应用层协调异步事件 |

> 💡 判断规则：应用层的方法签名往往是"动词+用例"，例如 `createOrder(...)`、`cancelOrder(...)`；若发现方法里充满了 `if/else` 业务判断，说明业务规则正在泄漏到应用层。

## 领域层 Domain

### 职责与作用

**领域层是整个架构的核心（Heart of the System）**，承载所有业务规则与领域知识。领域层的质量直接决定系统的业务表达能力和可维护性。

| 职责 | 说明 |
|------|------|
| 表达领域模型 | 用实体、值对象、聚合描述真实业务世界的概念与关系 |
| 承载业务规则 | 业务不变量、计算公式、状态流转约束等全部收敛于此 |
| 领域服务 | 处理不适合放在单个实体/聚合中的跨对象业务逻辑 |
| 领域事件 | 定义并发布领域内发生的事实，驱动其他上下文的响应 |
| 定义抽象契约 | Repository 接口等端口定义，供基础设施层实现（依赖倒置） |
| 领域知识沉淀 | 让代码直接反映业务语言（Ubiquitous Language），可读且可维护 |

**核心概念**：

| 概念 | 含义 |
|------|------|
| 实体（Entity） | 有唯一标识、有生命周期、状态可变化的对象 |
| 值对象（Value Object） | 无标识、靠属性值相等判断、不可变的对象 |
| 聚合（Aggregate） | 实体+值对象的边界集合，聚合根是外部访问的唯一入口 |
| 聚合根（Aggregate Root） | 聚合的边界守卫者，保证聚合内数据一致性 |
| 领域服务（Domain Service） | 跨多个实体的业务行为，无状态 |
| 领域事件（Domain Event） | 领域内已发生事实的封装，用于解耦与异步化 |
| 仓储接口（Repository） | 领域层定义的持久化抽象契约，实现由基础设施层提供 |

**关键原则**：

- ✅ 领域层是唯一允许存在复杂业务逻辑的层
- ✅ 依赖倒置：领域层定义 Repository 接口，通过该接口间接访问数据
- ✅ 领域对象可以持有值对象、自身状态和领域方法
- ❌ 禁止依赖 MyBatis Mapper、RedisTemplate、JdbcTemplate 等具体实现类
- ❌ 禁止使用 Spring 注解（`@Service`、`@Transactional` 等）污染领域对象
- ❌ 禁止出现"贫血模型"（领域对象只有 getter/setter，没有行为）

### 二级分包

| 子包 | 含义与职责 |
|------|------------|
| `model` | 领域模型，可再细分 `aggregate`（聚合根）、`entity`（实体）、`valueobject`（值对象） |
| `service` | 领域服务（DomainService），跨聚合/跨实体的纯业务规则实现 |
| `repository` | 仓储接口定义（抽象契约），由基础设施层实现 |
| `event` | 领域事件定义（事件类、事件类型常量）及发布入口 |
| `key` | 领域内使用的缓存 Key 常量定义（可选，保持命名统一） |
| `factory` | 领域工厂（可选），封装复杂聚合的创建逻辑 |
| `specification` | 规格模式（可选），封装可组合的业务校验规则 |

> 💡 判断规则：如果领域层代码改动需要动到数据库、改到框架配置，说明领域层已经被污染；反之，领域层应该可以脱离 Spring、脱离数据库独立测试。

## 基础设施层 Infrastructure

### 职责与作用

**基础设施层是"实现细节"的集合**，为领域层定义的抽象提供具体实现，为整个系统提供技术支撑。

| 职责 | 说明 |
|------|------|
| 持久化实现 | 实现 Repository 接口，完成数据库读写、ORM 映射 |
| 缓存实现 | Redis/Caffeine 等缓存的具体操作封装 |
| 消息队列 | MQ 生产者/消费者的技术封装与可靠发送实现 |
| 外部服务适配 | 第三方 API、其他微服务的 SDK 调用适配 |
| 技术配置 | 数据源、Redis、MQ、Nacos 等基础设施配置 |

**关键原则**：

- ✅ 基础设施层**依赖领域层**（实现其接口），而不是被领域层依赖
- ✅ Repository 实现类位于此层，接口位于领域层
- ✅ 允许使用 MyBatis Mapper、RedisTemplate、JdbcTemplate、RocketMQTemplate 等具体实现类
- ✅ 技术选型的变更（换数据库、换 MQ）只影响此层，不影响领域层
- ❌ 禁止把业务规则写在基础设施层（它是"服务员"，不是"决策者"）
- ❌ 禁止领域层反向依赖本层的具体类

### 二级分包

| 子包 | 含义与职责 |
|------|------------|
| `persistence` | 持久化相关，再细分：`mapper`（ORM 映射接口/XML）、`repository`（Repository 接口实现）、`entity`（DO 数据对象）、`converter`（DO ↔ 领域对象转换） |
| `messaging` | 消息队列封装：可靠发送、消费处理、消息补偿 |
| `external` | 外部服务/第三方适配层，屏蔽外部系统差异 |
| `client` | 调用其他微服务的 SDK 封装（Feign 等） |
| `config` | 基础设施配置类（数据源、缓存、MQ、序列化等） |
| `cache` | 缓存读写封装、缓存策略实现（可选） |

> 💡 判断规则：本层代码一换技术栈就要重写，这是正常的，甚至说明本层"名至实归"；如果换个数据库业务代码也要改，说明依赖倒置没有做好。

## 四层协作规则

### 依赖方向总览

| 层 | 依赖谁 | 被谁依赖 |
|----|--------|----------|
| Interfaces | Application、Domain | 外部调用方 |
| Application | Domain | Interfaces |
| Domain | 无（只依赖自身模型） | 其他所有层 |
| Infrastructure | Domain | 无（被 Spring 容器装配） |

### 依赖倒置原则（DIP）在四层中的体现

```
领域层定义接口：   OrderRepository（抽象，位于 domain）
基础设施层实现：   OrderRepositoryImpl（实现，位于 infrastructure）
应用层使用：       OrderRepository 接口（不关心实现细节）
```

- 数据访问的"方向"从领域层指向基础设施层（调用），通过接口反转成"领域层定义、基础设施层实现"
- 好处：领域层不感知数据库，测试时可轻松替换为内存实现

### 各层典型对象对照

| 层 | 典型命名 | 常见注解 | 示例 |
|----|----------|----------|------|
| Interfaces | `*Controller` / `*VO` / `*Request` / `*Listener` / `*Task` | `@RestController` `@RequestMapping` | `OrderController` |
| Application | `*ApplicationService` / `*DTO` | `@Service` `@Transactional` | `OrderApplicationService` |
| Domain | `*Aggregate` / `*Entity` / `*DomainService` / `*Repository` | 无（纯净） | `OrderAggregate` / `OrderRepository` |
| Infrastructure | `*RepositoryImpl` / `*Mapper` / `*DO` | `@Mapper` `@Component` | `OrderRepositoryImpl` / `OrderDO` |

### 分层协作时序（概念示例）

```
Controller  →  ApplicationService  →  DomainService / Aggregate
    │                │                        │
    │                │                        │  调用
    │                │                        ▼
    │                │              Repository（接口，领域层定义）
    │                │                        │  实现
    │                │                        ▼
    │                └────────────────  RepositoryImpl（基础设施层）
    │                                                    │
    └──────────── 返回 VO ───────────── 返回结果 ◀───────┘
```

## 主流分层变体对比

### 经典四层架构（本项目采用）

`interfaces → application → domain ← infrastructure`

- 结构直观、认知成本低，适合大多数团队和项目
- 是 Evans 原著思想的最常见落地形态

### 洋葱架构（Onion Architecture）

```
     外部依赖（DB/MQ/Web）
          ↓ 适配器
    Infrastructure
          ↓
    Application
          ↓
    Domain（最内核）
```

- 以领域层为同心圆圆心，依赖只允许由外向内
- 与四层本质一致，只是强调了"越靠近核心越稳定"

### 六边形架构 / 端口-适配器（Ports & Adapters）

```
        ┌── 入站适配器（REST/MQ/CLI）
        │        │
        ▼        ▼
    ┌─── 应用核心（Domain + Application）───┐
        ▲        ▲
        │        │
        └── 出站适配器（DB/Redis/外部API）
```

- 用"端口（接口）"和"适配器（实现）"解耦应用核心与外部世界
- 强调技术是中立的，可通过适配器随意替换
- 四层架构中的"依赖倒置 + Repository 接口"正是端口-适配器思想的具体应用

### 三者关系

| 架构 | 核心思想 | 与经典四层的关系 |
|------|----------|------------------|
| 经典四层 | 按职责分层，依赖单向 | 基础形态 |
| 洋葱架构 | 领域为核心，依赖向内 | 四层的深化表达 |
| 六边形/端口-适配器 | 端口解耦外部世界 | 四层中依赖倒置思想的系统化 |

> 💡 三者并不互斥，本质是同一思想的三种表述：**领域层纯净 + 依赖倒置 + 技术细节外置**。理解了四层，就理解了其他变体。

## 分层取舍建议

### 什么时候用完整四层

- 业务复杂、规则多变、需要长期演进的中大型系统
- 需要独立测试领域逻辑、可能更换技术栈的系统
- 团队对 DDD 有共识，愿意付出建模成本

### 什么时候可以简化

- 纯 CRUD 业务（无复杂规则）→ 可退化为三层（controller/service/mapper），避免过度设计
- 团队规模小、迭代极快、业务边界模糊的早期阶段
- 可以用"领域层 + 应用层合并"等折中方案，先跑起来再演进

### 常见反模式

| 反模式 | 表现 | 危害 |
|--------|------|------|
| 贫血模型 | 领域对象只有 getter/setter，规则全在 Service | 领域层形同虚设 |
| 失血模型 | 连领域对象都省略，直接用 DO 贯穿所有层 | 业务规则散落、无法复用 |
| 过度分层 | 简单 CRUD 也强行拆四层 | 代码量翻倍、难以维护 |
| 依赖倒置失效 | 应用层直接注入 Mapper | 领域层失去独立性 |
| 层间泄漏 | Controller 里写业务、Service 里写 SQL | 职责混乱、难以测试 |
| 大泥球 | 包结构不按层组织，新代码随意放置 | 架构形同虚设 |

### 落地建议

1. **先建模后分层**：分层是骨架，领域模型才是血肉，别让层约束绑架了模型表达
2. **从需求反推分层**：写代码前想清楚"这个判断属于业务规则还是用例编排"
3. **保持领域层纯净是底线**：其他层可以妥协，领域层的纯净性不可妥协
4. **分层规范要可检查**：把依赖方向写进 Code Review 检查清单
5. **必要时允许破例**：简单场景可局部简化，但要显式说明并保持整体一致

## 小结

DDD 四层架构的要点一句话总结：

> **接口层管"进出"、应用层管"编排"、领域层管"规则"、基础设施层管"实现"**，通过依赖倒置让领域层成为稳定、纯净、可测试的核心。

掌握四层架构，是理解洋葱架构、六边形架构以及各种微服务分层实践的基础。
